# Contextual Retrieval
*[[Based on Anthropic's Research](references/raw-contextual-retrieval)]*

## Introduction
Retrieval-Augmented Generation (RAG) is the standard architecture for grounding LLMs in external knowledge bases that exceed prompt limits. However, traditional RAG pipelines suffer from an architectural flaw: **context destruction**. Splitting long documents into isolated chunks (typically 200–800 tokens) strips away crucial global context—such as document titles, company names, section hierarchies, and temporal markers. Consequently, both vector search and lexical search frequently fail to retrieve relevant chunks.

**Contextual Retrieval** solves this by prepending concise, chunk-specific explanatory context (50–100 tokens) generated by a lightweight LLM to each chunk prior to embedding and indexing. Combined with hybrid search (Contextual Embeddings + Contextual BM25) and cross-encoder reranking, this approach reduces retrieval failure rates by up to **67%**, while Anthropic's prompt caching keeps the one-time indexing cost negligible ($1.02 per million document tokens).

## The Context Conundrum in Traditional RAG

### 1. The Token Horizon Heuristic: In-Context vs. RAG
Before deploying a RAG pipeline, assess knowledge base size:
* **Knowledge bases under 200,000 tokens (~500 pages):** Bypass RAG entirely. Pass the entire corpus into Claude's prompt window using [[prompt-caching|prompt caching]]. This reduces latency by >2x and operating costs by up to 90% without retrieval degradation.
* **Knowledge bases over 200,000 tokens:** Requires scalable chunk-based retrieval, where contextual degradation must be actively mitigated.

### 2. Context Loss in Chunking
When documents are segmented into standalone chunks, individual fragments lose their overarching referential integrity:
* *Example query:* "What was the revenue growth for ACME Corp in Q2 2023?"
* *Raw chunk:* `"The company's revenue grew by 3% over the previous quarter."`
* *Failure mode:* Vector embeddings and keyword indices cannot resolve `"The company"` to *ACME Corp* or `"the previous quarter"` to *Q1 2023*. The chunk is omitted from top-K retrieval candidates.

### 3. Limitations of Prior Contextualization Approaches
Earlier attempts to restore context have suffered significant shortcomings:
* **Generic Document Summaries:** Appending identical overall document summaries to every chunk provides very limited retrieval gains.
* **Hypothetical Document Embeddings (HyDE):** Generates hypothetical answers at query time; suffers from high latency and inconsistent performance.
* **Summary-Based Indexing:** Building hierarchical summary trees yields low recall in complex technical and factual benchmarks.

## Core Architecture: Contextual Retrieval

Contextual Retrieval operates during the document ingestion and indexing phase by generating chunk-specific context that situates each fragment within the complete source document.

```
┌────────────────────────────────────────────────────────┐
│ Full Document (e.g., 8,000 tokens)                      │
│ [Prompt-Cached in Claude 3 Haiku]                      │
└───────────────────────────┬────────────────────────────┘
                            │
              Situational Context Instruction
                            ▼
┌────────────────────────────────────────────────────────┐
│ Raw Chunk (e.g., ~800 tokens)                          │
└───────────────────────────┬────────────────────────────┘
                            │ LLM Contextualizer (~50-100 tokens)
                            ▼
┌────────────────────────────────────────────────────────┐
│ Contextualized Chunk:                                  │
│ "[Situational Context] + [Original Raw Content]"       │
└─────────────┬────────────────────────────┬─────────────┘
              ▼                            ▼
   Dense Vector Embedding          Sparse BM25 Indexing
  (e.g., Gemini / Voyage)          (Exact Term Matching)
```

### 1. Situating the Chunk
A lightweight model (e.g., Claude 3 Haiku) processes the entire document alongside the targeted chunk using a prompt designed exclusively for situational attribution:

```plaintext
<document> 
{{WHOLE_DOCUMENT}} 
</document> 
Here is the chunk we want to situate within the whole document 
<chunk> 
{{CHUNK_CONTENT}} 
</chunk> 
Please give a short succinct context to situate this chunk within the overall document for the purposes of improving search retrieval of the chunk. Answer only with the succinct context and nothing else.
```

### 2. Transformed Chunk Representation
The model generates 50–100 tokens of high-density context prepended directly to the chunk:
* *Raw chunk:* `"The company's revenue grew by 3% over the previous quarter."`
* *Contextualized chunk:* `"This chunk is from an SEC filing on ACME corp's performance in Q2 2023; the previous quarter's revenue was $314 million. The company's revenue grew by 3% over the previous quarter."`

### 3. Dual Indexing: Contextual Embeddings + Contextual BM25
The enriched chunk is fed into both retrieval modalities:
* **Contextual Embeddings (Semantic Search):** Encodes conceptual and topical nuances into dense vector space.
* **Contextual BM25 (Lexical Search):** Builds TF-IDF sparse indices with term-frequency saturation and length normalization. Crucial for exact identifiers, error codes (e.g., `"TS-999"`), SKU numbers, and named entities that semantic models conflate.

## Benchmark Results & Performance Gains

Evaluated using **$1 - \text{Recall}@20$** (the proportion of queries where the ground-truth chunk fails to appear in the top-20 retrieved candidates) across diverse corpora (codebases, ArXiv papers, scientific research, fiction):

| Retrieval Configuration | Failure Rate ($1 - \text{Recall}@20$) | Failure Reduction vs. Baseline |
| :--- | :---: | :---: |
| **Traditional Semantic Embeddings** (Baseline) | **5.7%** | — |
| **Contextual Embeddings** | **3.7%** | **-35%** |
| **Contextual Embeddings + Contextual BM25** | **2.9%** | **-49%** |
| **Contextual Embeddings + Contextual BM25 + Reranking** | **1.9%** | **-67%** |

*All tested embedding models (Voyage, Gemini Text 004, OpenAI) showed consistent failure reductions when contextualized, with Gemini Text 004 and Voyage demonstrating top-tier baseline performance.*

## Two-Stage Retrieval: Maximizing Precision with Reranking

While initial retrieval casts a wide net over millions of chunks, coarse search functions return candidate sets containing false positives. Reranking introduces a fine-grained relevance scoring stage before passing context to the generator LLM.

```
Query ──► [Hybrid Retrieval: Top 150 Candidates]
               (Contextual Embeddings + BM25)
                          │
                          ▼
             [Cross-Encoder Reranker]
             (e.g., Cohere / Voyage Rerank)
                          │
                          ▼
            [Top 20 Scored Chunks] ──► Final LLM Generation
```

### Two-Stage Pipeline
1. **Initial Hybrid Search:** Retrieve top candidates ($N \approx 150$) using rank-fused Contextual Embeddings and Contextual BM25.
2. **Cross-Encoder Scoring:** Pass the query and candidate chunks through a dedicated reranker (e.g., Cohere Rerank or Voyage Rerank) to compute deep cross-attention relevance scores in parallel.
3. **Top-K Truncation:** Select the top-K ($K = 20$) highest-scoring chunks and pass them into the prompt of the generative model.

### Latency vs. Cost Trade-offs
* **Latency Impact:** Adding a reranker introduces an extra round-trip network call (~100–300 ms).
* **Cost Efficiency:** Scoring 150 chunks with a dedicated reranking endpoint is significantly cheaper and faster than passing 150 irrelevant chunks into the generative model's inference context window.

## Implementation Heuristics & Cost Engineering

### 1. Cost Optimization via Prompt Caching
Without caching, passing an 8,000-token document repeatedly for every 800-token chunk would be cost-prohibitive. With Claude prompt caching:
* Load the source document into cache once.
* Reference cached tokens across sequential chunk requests.
* **Total one-time cost:** **$1.02 per million document tokens** (assuming 8k token documents, 800-token chunks, and 100-token generated context).

### 2. Chunking & Boundary Strategies
* Maintain chunk sizes around 500–800 tokens with slight overlap (e.g., 10–15%) to avoid splitting sentences across boundaries.
* Natural semantic boundaries (sections, headings, Markdown breaks) produce more coherent LLM-generated context than arbitrary token splits.

### 3. Contextualizer Prompt Tuning
* **Domain Glossaries:** Inject domain-specific terminology, entity maps, or acronym directories into the contextualizer prompt when chunks contain ambiguous abbreviations.
* **Boundary Separation for Generation:** When passing retrieved chunks to the final generation model, clearly distinguish prepended context from the raw chunk text using structured markers (e.g., XML `<context>` vs. `<content>` tags) to prevent the model from misattributing metadata as primary source text.

### 4. Context Budgeting ($K=20$)
Anthropic's ablations across top-5, top-10, and top-20 retrievals demonstrated that providing **20 chunks** yields the highest response accuracy without inducing attention distraction or context rot in modern frontier models.

## Conclusion & Best Practices Checklist

The benefits of retrieval optimizations **stack cumulatively**:

- [ ] **Bypass RAG for small corpora:** If document collection is $< 200\text{k}$ tokens, rely on full-context prompt caching.
- [ ] **Contextualize chunks at ingestion:** Prepend 50–100 tokens of LLM-generated situational context to every chunk.
- [ ] **Leverage prompt caching during ingestion:** Cache the base document to keep preprocessing costs near ~$1.00/1M tokens.
- [ ] **Deploy hybrid retrieval:** Combine dense vector embeddings (e.g., Voyage or Gemini Text 004) with sparse BM25 lexical search.
- [ ] **Integrate cross-encoder reranking:** Retrieve the top 150 candidate chunks, rerank via Cohere/Voyage, and pass the top 20 to the generator.
- [ ] **Run domain-specific evals:** Continuously measure retrieval accuracy ($1 - \text{Recall}@K$) and end-to-end task performance to balance latency against retrieval precision.
