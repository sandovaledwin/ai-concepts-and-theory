# Prompt Engineering (OpenAI)
*[[Based on OpenAI's API Guide](references/raw-prompt-engineering-openai)]*

## Introduction
**Prompt engineering** is the process of writing effective instructions so a model consistently generates content that meets your requirements. Because model output is non-deterministic, prompting is part art and part science — but techniques and best practices make results repeatable.

Two rules underpin production prompting:

* **Pin model snapshots** (e.g. `gpt-4.1-2025-04-14`) so behavior doesn't drift under you.
* **Build tests and eval suites** around prompts, so you can measure regressions when iterating or upgrading models.

## Main Points

### 1. Choosing the Right Model (and Prompting It Correctly)
* **Reasoning models** generate an internal chain of thought, excel at complex multi-step tasks, and are slower/pricier. Think of them as a **senior coworker**: give them a goal and trust them with the details.
* **GPT models** are fast and cost-efficient but benefit from **explicit, precise instructions**. Think of them as a **junior coworker**: spell out the specific output you want.
* **Large vs. small (mini/nano)** models trade speed and cost against intelligence and cross-domain reasoning.
* Prompting techniques are not portable: different model types — even different snapshots in the same family — may need different prompts.

### 2. Message Roles and the Chain of Command
Instructions carry different levels of authority, mirroring a function definition and its arguments:
* **`developer`** (or the `instructions` parameter) — rules and business logic authored by the application builder; prioritized ahead of `user` messages. Analogous to a **function definition**.
* **`user`** — inputs and configuration the instructions apply to. Analogous to **function arguments**.
* **`assistant`** — content generated by the model.

Two gotchas: the `instructions` parameter applies **only to the current response** (it is not replayed across turns when using `previous_response_id`), and information ordering matters for caching (see below).

### 3. Prompts Are Code, Not Configuration
Treat production prompts like source code, not remote objects:
* Keep **prompt builders in a small module** next to the feature they serve.
* Use **typed arguments or schemas** for dynamic values (customer data, files, task options).
* Add **fixtures, tests, and eval checks** before changing a production prompt.
* Roll changes out through your **normal deployment system** — feature flags or config for staged releases.
* OpenAI is **deprecating reusable prompt objects** (`v1/prompts` scheduled to shut down **Nov 30, 2026**); new work should live in application code.

### 4. Prompt Anatomy: Markdown + XML
Markdown headers communicate hierarchy and readability; XML tags delineate where a block of content begins and ends (and attributes can carry metadata). A `developer` message generally follows this order:

1. **Identity** — purpose, communication style, high-level goals.
2. **Instructions** — rules, what to do, and explicitly what *never* to do (sub-sections as needed, e.g. function calling).
3. **Examples** — sample inputs paired with the desired output.
4. **Context** — proprietary or out-of-training data, plus anything specific to this request. Best placed **near the end**, since it varies per call.

```text
# Identity
You are a coding assistant that enforces snake_case variables in JavaScript.

# Instructions
* Use snake_case names (my_variable), not camelCase (myVariable).
* Declare variables with the older `var` keyword for legacy browser support.
* Return only code, no Markdown formatting.

# Examples
<user_query>How do I declare a string variable for a first name?</user_query>
<assistant_response>var first_name = "Anna";</assistant_response>
```

### 5. Cost & Latency: Prompt Caching
Put content you reuse across requests **at the very beginning of the prompt** *and* among the first parameters in the JSON request body. This maximizes cache hits, cutting both cost and latency (see [[prompt-caching|Prompt Caching]] for exact KV prefix rules and cost modeling).

### 6. Few-Shot Learning
Rather than fine-tuning, include a handful of input/output examples so the model implicitly "picks up" the pattern. Show a **diverse range** of inputs with their correct outputs — a curated set of canonical cases beats a laundry list of edge cases. Examples normally live in the `developer` message, often wrapped in XML tags with matching `id` attributes.

### 7. Adding Context (RAG) and the Context Window
* Add external context to give the model data outside its training set, or to constrain it to a specific set of resources.
* This is **retrieval-augmented generation (RAG)** — whether you fetch from a vector DB and paste the text, or use a built-in file-search tool over uploaded documents.
* Everything must fit the **context window**, measured in tokens (roughly 100k up to ~1M for newer models). Plan retrieval around that budget rather than stuffing.

### 8. Domain Playbooks
**Coding**
* Define the agent's role and workflow explicitly; state when *not* to use certain modes (e.g. interactive execution).
* Provide **concrete tool-use examples** instead of prose descriptions of tools.
* Require testing/validation (unit tests, Python commands) — and warn that `apply_patch` may report "Done" even on failure.
* Set **Markdown standards**: inline code, fenced blocks, lists, tables; backticks around paths, functions, classes.

**Front-end**
* Preferred libraries: **Tailwind CSS / shadcn/ui / Radix Themes**, **Lucide / Material Symbols / Heroicons**, **Motion** for animation.
* Zero-to-one apps: use a self-critique loop — build an internal rubric (5–7 categories), evaluate the candidate solution against it, and iterate until it clears the bar; favor simplicity and avoid external frameworks unless asked.
* Large codebases: supply instructions for **Principles** (visual quality, reusable components, consistency), **UI/UX** (typography, color, spacing, hover/empty/loading states, accessibility), **Structure** (file/folder layout), **Components** (wrapper examples, backend-call separation), **Pages** (layout templates), and **Agent Instructions** (confirm assumptions, scaffold, enforce standards, integrate APIs, test states, document).

**Agentic tasks**
* **Planning and persistence** — instruct the agent to resolve the whole query before yielding: decompose into sub-requests, reflect after each tool call, and don't stop at partial completion.
* **Preambles for transparency** — explain *why* a tool is being called, but only at notable steps.
* **Progress tracking** — use a TODO tool or rubric so multi-step workflows don't silently drop steps.

## Conclusion
Prompt engineering is ordinary software engineering applied to natural language: version it, test it, cache the stable parts, and structure it clearly. The main judgment call is **how much to specify** — precise instructions for GPT-style models, high-level goals for reasoning models — and knowing which of the two you are talking to.
